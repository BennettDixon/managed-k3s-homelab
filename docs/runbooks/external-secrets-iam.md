# Runbook: external-secrets (ESO) IAM identity

Brings the AWS identity that external-secrets (ESO) authenticates as under
terraform, and scopes it to least privilege. Terraform:
`terraform/iam-external-secrets.tf` + outputs in `terraform/outputs.tf`. The
ClusterSecretStore it feeds: `infrastructure/configs/secret-stores.yaml`
(unchanged by this work — the Secret NAME stays `aws-creds`; only its two key
VALUES change, and only at cutover).

## What ESO uses today, and the problem

ESO authenticates to AWS Secrets Manager with a **static IAM user access key**
held in the k8s Secret `aws-creds` (namespace `external-secrets`, keys
`aws_access_key_id` / `aws_secret_access_key`), referenced by the
ClusterSecretStore `aws-secrets-manager`. That Secret is applied **out of band**
(ESO cannot source its own bootstrap credential — chicken/egg), so it is not in
git and never has been.

- **Before (the problem):** the identity behind that key was created in the AWS
  console and is entirely unmanaged by terraform. It carries the AWS managed
  policy **`SecretsManagerReadWrite`** — account-wide **read AND write** to
  *every* secret in the account. One access key, ~600 days old.
- **After (this runbook's end state):** a terraform-managed IAM user
  `k3s-external-secrets-reader` with a dedicated policy allowing only
  `secretsmanager:GetSecretValue` + `secretsmanager:DescribeSecret` (read-only)
  on **exactly the 13 secrets** ESO consumes — no writes, no account-wide reach.
  ESO issues no `PushSecret` anywhere in this repo, so read-only is complete.

The 13 secrets (each an existing `terraform/main.tf` module; the policy
references their `.secret_arn` outputs, so no account-id literal lands in this
public repo) map one-for-one to the live ExternalSecrets:

| Secrets Manager name | terraform module | consuming namespace(s) |
| --- | --- | --- |
| `k3s_harbor_admin_password` | `harbor_admin_password_secret` | harbor |
| `k3s_harbor_docker_pull_default` | `default_harbor_docker_pull_secret` | personal-site |
| `k3s_harbor_docker_pull_personal_site` | `personal_site_harbor_docker_pull_secret` | personal-site |
| `k3s_harbor_docker_pull_jobs` | `jobs_harbor_docker_pull_secret` | jobs-mcp |
| `k3s_harbor_docker_pull_knowledge` | `knowledge_harbor_docker_pull_secret` | knowledge-mcp |
| `k3s_jobs_mcp_bearer_token` | `jobs_mcp_bearer_token_secret` | jobs-mcp |
| `k3s_jobs_mcp_webhook_secret` | `jobs_mcp_webhook_secret` | jobs-mcp |
| `k3s_jobs_mcp_n8n_api_key` | `jobs_mcp_n8n_api_key_secret` | jobs-mcp |
| `k3s_knowledge_mcp_caller_tokens` | `knowledge_mcp_caller_tokens_secret` | knowledge-mcp |

to the policy `Resource` list in `terraform/iam-external-secrets.tf` — otherwise
ESO gets AccessDenied for it. If ESO ever gains a `PushSecret`, add
`secretsmanager:PutSecretValue` (and re-scope) at that time.

## MERGE GATE — this PR is safe to merge; the CUTOVER is not automatic

This PR is **terraform-only**. **Nothing reconciles from it** — Flux does not
run terraform, and the new IAM user/key exist only after an operator apply.
Merging changes **nothing live**: ESO keeps using the OLD key until you run the
cutover below.

Do **NOT** run the cutover until you are ready and watching. A bad credential in
`aws-creds` takes the ClusterSecretStore NotReady, every ExternalSecret stops
syncing, and — because the apps Kustomization runs `wait: true` — an unready
ExternalSecret **freezes Flux reconciliation cluster-wide**. That is why the
cutover is gated, reversible, and keeps the old key alive until the new one is
proven.

No new terraform variables are introduced (the access key is generated by AWS),
so `terraform.tfvars` / `terraform.tfvars.empty` are unchanged.

## Cutover (gated operator step)

Run from `terraform/`, with the backend initialized as usual (`state.config`).

**0. Live AWS SSO session** (required before any apply — see CLAUDE.md):

```bash
aws sso login
aws sts get-caller-identity   # confirm the expected account/role
```

**1. Back up the CURRENT `aws-creds` so rollback is possible.** The old secret
access key half is unrecoverable once lost — capture it now, to a file OUTSIDE
this repo (or one that is gitignored), and delete it once cutover is confirmed:

```bash
kubectl -n external-secrets get secret aws-creds -o yaml > ~/aws-creds.OLD.yaml
```

**2. TARGETED apply of ONLY the new resources.** Full applies stay forbidden
while the Lightsail proxy drift is parked (STATUS) — target the four new
addresses so nothing else is in the plan:

```bash
terraform apply \
  -target=aws_iam_policy.external_secrets_reader \
  -target=aws_iam_user.external_secrets_reader \
  -target=aws_iam_user_policy_attachment.external_secrets_reader \
  -target=aws_iam_access_key.external_secrets_reader
```

Expect **adds only — 4 to add, 0 to change, 0 to destroy.** The 13 secret
modules the policy references already exist in state and must show as
unchanged. **If the plan wants to destroy ANYTHING (especially the Lightsail
public proxy), STOP** — you have run a non-targeted apply.

**3. Read the new key and write it into `aws-creds`.** The values come straight
from `terraform output -raw` via command substitution, so the plaintext never
appears literally in your shell history (history stores the `$(...)`
expression, not the resolved value — for extra care, `set +o history` for the
session). Never `echo` the values:

```bash
kubectl -n external-secrets create secret generic aws-creds \
  --from-literal=aws_access_key_id="$(terraform output -raw external_secrets_reader_access_key_id)" \
  --from-literal=aws_secret_access_key="$(terraform output -raw external_secrets_reader_secret_access_key)" \
  --dry-run=client -o yaml | kubectl apply -f -
```

**4. Force a re-sync and VERIFY before touching the old key.** ESO reauths on
its own cadence; force it so you are not waiting on `refreshInterval`:

```bash
# ClusterSecretStore must stay Ready with the new creds (it fails closed if not)
kubectl get clustersecretstore aws-secrets-manager

# Nudge every ExternalSecret to re-pull now
for ns in jobs-mcp knowledge-mcp kube-prometheus-stack personal-site harbor tailscale; do
  kubectl -n "$ns" get externalsecret -o name | while read es; do
    kubectl -n "$ns" annotate "$es" force-sync="$(date +%s)" --overwrite
  done
done

# EVERY row must read STATUS=SecretSynced, READY=True
kubectl get externalsecrets -A
```

Do not proceed until the store is Ready and **all** ExternalSecrets are
`SecretSynced`. A `SecretSyncedError` or a NotReady store means the new key is
wrong or under-scoped — roll back (below) and investigate; ESO keeps serving the
last-good synced values in the meantime (existing k8s Secrets are not deleted on
a failed refresh), which is your safety margin.

**5. Deprovision the OLD identity — only after step 4 is green.** The old user
is NOT terraform-managed; do this in the AWS console/CLI against the old
user/key you identified. Deactivate first (reversible), settle for a cool-down
(e.g. a day) to confirm nothing else used that key, then delete:

```bash
# reversible: flip the old key off but keep it
aws iam update-access-key --user-name <OLD_USER> --access-key-id <OLD_KEY_ID> --status Inactive
# after the cool-down: delete the key, detach SecretsManagerReadWrite, delete the user
```

Then delete the local backup from step 1.

## Reversibility / rollback

The OLD key stays **active** through steps 2–4 — cutover is a Secret value swap,
not a deletion. If anything looks wrong at step 4:

```bash
kubectl apply -f ~/aws-creds.OLD.yaml      # restore the previous credentials
```

ESO reauthenticates with the old key and resyncs. The new terraform-managed
user can sit unused (it costs nothing) until you retry, or be removed with a
targeted `terraform destroy` of the same four addresses.

## Approach: recommended vs alternative (operator's call at review)

- **RECOMMENDED — this PR: a dedicated new terraform-managed user + gated
  cutover.** Declarative, least-privilege from birth, consistent with how every
  other credential in this repo is handled, and a clean break from the ad-hoc
  ~600-day-old console key. Cost: the one-time credential swap above, which
  carries the freeze risk if fumbled — hence the gate, the pre-cutover backup,
  and the keep-old-key-alive-until-proven ordering.
- **ALTERNATIVE — `terraform import` the existing user and just tighten it.**
  Import the current IAM user + its policy attachment into state, detach
  `SecretsManagerReadWrite`, attach the same scoped read-only policy. **Lower
  operational risk: no credential swap, so no `aws-creds` change and no
  cluster-wide freeze window** — the permissions narrow under the running key.
  Downsides: it codifies an ad-hoc, ~600-day-old identity into terraform and
  does nothing about that key's age (rotation stays a separate chore); and
  `aws_iam_access_key` can only be imported id-and-status, never its secret
  half, so state won't hold a usable secret for that key. Pick this if avoiding
  the cutover window matters more than retiring the old key.

Either way the security win is the same: the ESO identity goes from account-wide
`SecretsManagerReadWrite` to read-only on 13 named secrets.
